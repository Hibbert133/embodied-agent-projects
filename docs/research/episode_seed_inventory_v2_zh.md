# 环境种子登记核验 v2

本阶段修复已确认的登记解析缺陷：仅收集区间端点会漏掉嵌套两元素数组的内部。旧冻结代码、历史收集及其较晚补充审计保持原样；本入口不追认旧预检完整，也不改写任何研究结论。

## 范围及语义

入口为 `scripts/check_episode_seed_scope_v2.py`，参数为查询闭区间及一个不存在的仓库内输出目录。查询只读，输出不创建预留，也不授权采集。实际新试验仍须单独冻结种子、方案、全部费用和收集器；不得用本次查询替代采集前的新快照。

来源为全部配置 JSON、输出树的 `manifest.json`、协议目录中名称含 seed 的 JSON、docs 下 Markdown、AGENTS.md 和 RESEARCH_PLAN.md；追踪其中显式 seed_registry 引用到仓库内 JSON／Markdown，并保存每份文件的字节数和 SHA-256。原始轨迹、结果大文件和任意 Python 种子生成逻辑不在解析范围。报告只保证该登记范围内的检查，不能证明不存在未登记的使用。

普通 seeds 列表视为显式成员；range／interval、嵌套列表中的数值对和旧 reserved 列表按闭区间处理。种子登记表内未命名的两元素分区保守视为区间。起始种子缺少显式末尾／数量、但同对象有合法后续预留区间时，保守封住从起始值至预留末尾的整个包络；这不声称其中每个种子都已实际执行。原预留不会因为失败、封存或新方案而自动释放。

算法噪声、bootstrap 等命名空间仍出现在目录中，但不会当作环境种子冲突。明确的 episode/environment/task 种子叶节点优先于祖先的算法命名空间。未知 generation 名称不能被宽泛排除。哈希、布尔元标志和计数字段不当作分配；明确 seed 字段的布尔值／浮点／空值、非法范围、缺失引用、越界引用、无法读入的文件等使结论成为 INDETERMINATE。

Markdown 是保守补充：识别种子／预留相关行内的区间与非负整数；忽略 ISO 日期及负的控制命令／损失标量。它可能把同一行的费用数字也标记为“可能的种子”，导致保守阻止，需要人工解释而非静默忽略。源码或登记变化后必须重新核验。

## 独立检查与局限

审计使用迭代 JSON 遍历和逐条来源证明，不调用生产解析器；逐一核对区间内部覆盖、JSON 指针、命名空间、文件哈希和闭区间相交结论。纯数组／临时文件测试包括历史嵌套错误、旧分区写法、端点伪造、引用环、缺失／越界、非法计数、日期、中文紧邻数字及来源变更。独立实现共享公开的格式约定和词表，不能排除共同规格错误。

开发中四次检查未通过的记录保留：哈希元数据误读、旧分区内部遗漏、审计对前导零的文本证明缺陷，以及审计将区间 count 当种子的缺陷。前两次单元测试完整终端日志及四次检查耗时未保存，记录明确标为缺失；后续正式验证保存日志、源码哈希和耗时。历史采集从未在本阶段重跑。

本阶段新增环境交互、重置、物理帧、模型拟合、策略查询、种子分配、在线 LLM API 均为零。工程检查通过不代表新模型具有预测能力，不代表完整任务收益或算法新颖性；CCF A 研究目标仍未完成。
